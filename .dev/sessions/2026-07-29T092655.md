Reworked the Song Schema Playground: its validator now mirrors the rules Song enforces at registration, its preview reads as a reference rather than a schema dump, and findings are located in the editor. Verified throughout against the checked-out song submodule, including Song's own base-schema fixture (`validation/dynamic-analysis-type/rendered-schema.json`) and its registration tests.

- **Validation matches Song.** `lib/validateSongSchema.ts` mirrors `analysisTypeRegistration.json` and `AnalysisTypeService`: the schema body allows only `type`, `definitions`, `properties`, `required`; `type` must be `object`; the six base-owned top-level names are rejected (`studyId`, `analysisState`, `analysisType`, `analysisTypeId`, `files`, `analysisId`); `experiment` must be an object when present; `required` must be unique strings; names may contain dots; `registration` is reserved. Fixed drift found against the checkout: `samples` and `study` were flagged as base-owned (`samples` was dropped from Song's forbidden list by the base-schema refactor already in the pin, `study` was never in it), the three hard rejections above were unflagged, and dots in names were rejected although Song allows them. Errors and warnings are separate lists, so a schema Song would reject still previews while it is being fixed.
- **Three silent failures now warn.** A misspelled keyword inside a property definition (`pooperties`, `requred`, `Enum`): JSON Schema ignores keywords it does not recognise, so Song accepts the registration and the misspelled rule constrains nothing. The warning names the nearest real keyword when one is within two edits, and `x-` keys pass as the conventional extension escape hatch. Paired with it, an object declaring `required` while defining no `properties` at all now warns too; that check previously sat inside the branch that needed `properties` to exist, so the exact case where a typo hid the keyword produced no finding. A conditional requiring a property the object never defines: Song accepts it but checks presence only, leaving the value unconstrained. And a stray key in the registration envelope (a `description` next to `name`): the request carries only name, schema, and options, and since Song registers no mapper of its own and leaves the MVC converters alone, Spring's deserialization drops anything else without an error, so the server gives the author no signal.
- **Preview.** One table per object, each row a field definition. It resolves `definitions` + `$ref` and folds in `allOf`, so a field reusing a definition shows that definition's constraints, and an unresolvable pointer is an error since Song's schema build fails on it. Conditionals are read out in full (nested `if`/`then`/`else`, draft-07 `dependencies`), with negated branches phrased as negatives, and sit below the fields they govern. Key-level keywords surface as object notes. A field a conditional makes required is marked conditional, not optional. Constraints read as English ("1 to 2 items", "minimum 0"). Objects below the first level open inline from the row that names them, so the analysis type and its top-level objects are the outline and anything deeper is drilled into in place. An array's item table is headed "each item in workflow.inputs", since the item shape is not a field and carries no required badge. Required answers yes, conditional, or no. Enum values are wrapped chips, long patterns truncate with the full value on hover, and `description` renders as prose in the body font.
- **Findings are located in the document.** Every finding carries a JSON path; new `lib/locateJsonPath.ts` maps a path to an offset range; a CodeMirror plugin tints the line and underlines the key, with the message on hover. Unparseable documents fall back to lang-json's `jsonParseLinter` for the position, which avoids reading offsets out of browser-specific `SyntaxError` messages. No new dependencies: that linter has no lint runtime and decorations come from the already-declared view package. Validation runs inside the plugin against the document rather than being pushed in from React, so a highlight cannot lag the text, and a path whose deepest segment is missing falls back to the deepest key that matched, so a highlight is either right or absent.
- **Templates.** Both carry descriptions so Load Demo shows the pattern. The demo's `then` branch required `causeOfDeath` and `survivalTime` without defining either, so it now defines them (enum, non-negative integer).
- **Docs.** Building Song Schemas gained a Descriptions entry (annotations are allowed inside `properties`, never in the schema body) and a note that a conditional's targets need defining. The playground page keeps a short Limitations note and delegates detail to the Song reference; the `experiment` version caveat was cut as too deep for that page, with the reasoning in `roadmap.md`. Download JSON is gone from this playground, leaving Copy JSON as the primary action; the Dictionary Playground keeps its download.
- **Incidental.** The Dictionary Playground rename to `02-lectern-dictionary-playground.mdx` had left three inbound links on the old slug, breaking the build under `onBrokenLinks: "throw"`; Building Dictionaries, the playgrounds overview, and the workshop Extension Task now use the new slug and name. The editor toolbar and preview header took different heights, so their bottom borders did not line up; both now share `--song-bar-height`, though they can still diverge if the toolbar wraps at a very narrow editor width.

Reviewed the charts module source and rewrote `docs/charts.md` against it, rather than against the README it was ported from. The README turned out to be both incomplete (three of five exports undocumented, two of three `ChartsProvider` props missing) and wrong in its quick start. Also found `modules/charts/maintainer-docs/`, which documents `NetworkNodesChart`, the architecture, and the theming system, and carries the only two screenshots of the library in use.

- **The quick start could not have run.** `BarChart`'s view calls `calculateCustomTickValues(data, theme.axisBottom)` unguarded, so a `BarChart` without a `theme` object throws a `TypeError` the moment data arrives; `theme` is also non-optional in `BarChartProps`. The README omitted it. Fixed in both the docs page (with a caution admonition) and the README, along with the two smaller errors already noted (`ArrangerDataProvider` import, `style={{ height }}`). `NetworkNodesChart` has the same shape: its view reads `theme.sortAlphabetically` unguarded.
- **Axis legends default to placeholders.** `arrangerToNivoBarChart` merges the consumer theme over defaults that set `legend: 'Axis-Bottom-Legend'` and `'Axis-Left-Legend'`, so a chart with no legends renders that literal text. Documented, since the bar screenshot shows a consumer that had to pass empty strings.
- **`NetworkNodesChart` documented** (verified against source and the maintainer docs): no `fieldName`, reads `network.nodes`, calls `requireNetworkSearch()` on mount, `sortAlphabetically` defaults to true, `maxBars` defaults to unlimited. `HeadlessChart` stayed out: it is exported but its body is entirely commented out.
- **Corrections to what the page previously claimed.** `maxSegments` caps inner-ring *categories*, not segments, and every value under a displayed category is drawn. `SunburstChart` accepts a `theme` prop that `SunburstView` never reads, so the page now says so instead of listing it as configuration. `sortByKey` drops any bucket not in the list, which makes it a filter as well as a sort. `mapper` returning nothing drops that bucket, same story.
- **New material, all verified in source:** the single-GraphQL-query model; `disableIncludeMissing` and `loadingDelay`'s 50 ms default; the default 12-colour d3 palette; the three fallback strings (`Loading...`, `Error`, `No Data Available`); `__` for nested field names; the full ES-type-to-aggregation-type table, including `date` counting as numeric and an unmapped field silently falling back to categorical; `from` inclusive / `to` exclusive ranges (the README's example had a gap at 18–19 and double-counted 65); colour persistence in `sessionStorage` under `arranger-charts-<fieldName>`; zero-count buckets rendering a minimum bar with a `Too few` tooltip; the tooltip and badge CSS hooks; one registration per field name per provider.
- **Screenshots.** `maintainer-docs/bar.png` and `sunburst.png` copied to `docs/assets/charts-bar.png` and `charts-sunburst.png` and placed under the `BarChart` and `SunburstChart` headings, captioned to note the surrounding card and title are the consumer app's, not the library's. Both emit into the build.
- **Code findings, not applied** (docs-only session; they are behaviour changes): `validateAggregationsType` guards on `queryProps?.variables?.range`, singular, so the intended "categorical fields reject `ranges`" rule never fires and `ranges` is silently ignored instead — the docs page says "not used", which is true either way. `theme` being a hard requirement that throws rather than defaulting. `SunburstChart`'s dead `theme` prop. `HeadlessChart` exported as a no-op. `components.TooltipComp` declared but not wired (already flagged in a source comment). Registration keyed by field name means two charts on one field with different `ranges` silently share the first chart's config, and deregistering either removes the field for both.
- **`maintainer-docs.md`** had `mapping={...}` where the prop is `mapper`; corrected.
