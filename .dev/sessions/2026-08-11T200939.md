# 2026-08-11: `/products/` gets its flow diagram, `StackDiagram`

Nothing pushed. Implements `products-diagram-plan.md` phase 1 in full (order of
work items 1-6, 8); phase 2 (the platform lens) and the home-page reuse
question are still open, per the plan.

## The diagram

`data/componentFlow.ts`: seven nodes on two lanes (Lectern → Lyric → Maestro →
Arranger → Stage on top, Song → Score underneath, Song also feeding Maestro),
Control drawn as a dashed band around all of it rather than an eighth node.
Coordinates are a 0-100 x/y space shared by the SVG edge layer and the
percentage-positioned node cards, so both scale together on resize with no JS
recomputing anything.

`StackDiagram.tsx`, rendered between `Hero` and `ComponentTable` on
`/products/`: each node is a real `Link`, Pointer Events for hover (not
`onMouseEnter`, same `@docusaurus/Link` bug `HeroDiagram` already worked
around), `utils/floatingTooltip.ts` for the tooltip. Hovering or focusing a
node dims the rest and lights only its own edges; hovering or focusing the
Control tag dims nothing, since the band applies to everything already on
screen. `getHref` is a prop (defaults to `#<id>`, scrolling to the matching
`ComponentTable` row) rather than hardcoded, so a later home-page instance can
pass a link out to `/products/#<id>` instead without a rewrite — not built
here, per the plan's own open question about whether home needs a second
orientation device alongside `HeroDiagram` and `LogoCarousel`.

Two-way highlight with `ComponentTable` reuses `ComponentHighlightContext`
rather than a new provider: both `StackDiagram` and `ComponentTable` now read
and write `highlightedComponent` off the same axis, scoped to `/products/` by
wrapping just that pair in `pages/products/index.tsx`. `highlightedPlatform`,
the context's other axis, is untouched — it's what a phase 2 lens would hang
off later.

## The two inferred edges, checked rather than left open

The plan flagged two edges as inference: whether Lectern feeds Song as well as
Lyric, and whether Score sits downstream of Song or beside it. Checked against
the submodules' own docs before shipping either as fact:

- `lectern/docs/01-overview.md` names only Lyric as what Lectern "typically
  works with" for submission validation. Song's README lists Lectern once, in
  a general related-projects table every component appears in, not a
  validation dependency. **No edge from Lectern to Song.**
- `score/docs/overview.md` and `score/docs/setup.md` describe Song as managing
  "metadata for files stored by Score" and require Song running for Score's
  own dev stack. **Score is downstream of Song**, matching the plan's
  original guess. Both resolutions are written into `componentFlow.ts`'s own
  header comment, not just here.

## Mobile: built, screenshotted, then rebuilt

Order of work said screenshot before deciding, not decide first. The wide
left-to-right layout, scaled down in place, ran the right three nodes and part
of the Control band off a 375px screen — confirmed with a real Chrome capture,
not assumed. `data/componentFlow.ts` gained `flowNodesMobile` (same seven
nodes, same edges, rotated into two vertical lanes merging into a single
column at Maestro) and matching `flowBandMobile`/`flowControlLabelMobile`.
`StackDiagram.tsx` factors the shared render into `StackDiagramLayout` and
renders it twice; `_stack-diagram.scss` shows exactly one copy per breakpoint
(`tablet-up` / `mobile`), so nothing is lost, no node ever needs a smaller
font than the mobile variant already sets, and neither JS nor a resize
listener decides which one is live — `display: none` does, which also drops
the hidden one out of the tab order for free.

The segmented-control alternative the plan offered (filter the table instead
of drawing the diagram) wasn't needed: the rotated layout reads cleanly at
375px in the capture, so per the plan's own preference, one component stayed
one component.

## Follow-up, same day: infrastructure, and the heading cut

Two requests against the shipped diagram, both on the developer's direct
call rather than the plan:

- **Datastores drawn in.** MongoDB under Lectern, PostgreSQL under Lyric and
  Song, each a second line on the card rather than a separate node — they're
  private to their owner, nothing downstream connects to them, so they aren't
  a step in the flow. Sourced from each component's own setup docs (not
  assumed from what's typical for a service like it): `lectern/docs/02-Setup.md`,
  `lyric/docs/01-overview.md`, `song/docs/00-overview.md`. The Elasticsearch/
  OpenSearch index between Maestro and Arranger is different in kind — it
  belongs to neither side — so it's its own stop in the flow
  (`data/componentFlow.ts`'s `flowSearchIndex`/`SEARCH_INDEX_ID`, a non-`Link`
  annotation that still dims and lights with its two neighbours). Fitting it
  in required widening the Maestro-Arranger gap (`flowNodes`' x: 54→50 and
  76→80), which is the only position that moved.
- **Heading and lede cut.** `StackDiagram` had grown its own "How the
  components fit together" / "Distributed metadata becomes..." intro,
  mirroring `HomeCapabilities`' banded-section convention; removed on
  request, so the diagram now sits directly under the hero with no
  introduction. The section kept an accessible name via `aria-label` on the
  `<section>` itself rather than `aria-labelledby` pointing at a now-deleted
  heading id.

## Second follow-up, same day: real datastore icons

The MongoDB/PostgreSQL/OpenSearch/Elasticsearch labels above shipped as text
only; asked for the actual marks. This repo had no icon package and the
site's own component icons are custom illustrated cubes, not real product
logos, so there was no existing asset or convention to reuse — asked the
developer how to source them rather than guessing (fetch from the web,
hand-draw generic glyphs, or a package), who picked adding
[`simple-icons`](https://simpleicons.org) (CC0-1.0, one new dependency in
`package.json`/`package-lock.json`). Its `icons/*.svg` files have no `.js`/
`.mjs` sibling to import as a module, so rather than fight the bundler over
raw-SVG imports from `node_modules`, the four paths needed (`postgresql`,
`mongodb`, `elasticsearch`, `opensearch`) were copied once into a new
`data/techIcons.ts` (viewBox + path string, `fill="currentColor"` at render
time) — inline SVG the same way the rest of the diagram already is, and the
one place in the codebase that would need touching if `simple-icons` is
upgraded and a mark changes. `componentFlow.ts`'s `flowNodeStorage` and
`flowSearchIndex`/`flowSearchIndexMobile` now carry an `icon`/`icons` key
alongside the label; `StackDiagram.tsx` renders them via a small
`TechIconGlyph` helper, colored to match the muted label text next to them
and brightening the same way on hover. Verified with a zoomed-in screenshot
(3x device scale) that all four marks are actually legible at the size
they're drawn, not just present in the DOM.

Also fixed while in there, not requested but found doing it: `StackDiagram`
had copied `HomeCapabilities`' `section` class (3rem/48px padding) *and* sat
inside `.ProductsPage .container`'s own 5.2em/75.2px vertical padding, a
combination `ComponentTable` never carried — the two stacked into ~246px of
dead space at the diagram/table seam on a 1440px viewport, flagged as
inefficient use of vertical space. Dropped `section`; `ComponentTable`'s own
convention (`.container` alone) is now what both share. Separately, the
diagram's `aspect-ratio` box was stretching to `.container`'s own full width
(up to 1344px) while its node cards stayed fixed pixel size, so the box grew
tall for no reason at wide viewports (562px measured) — capped
`.StackDiagram__diagram--desktop` at `max-width: 880px`, centered, which
brought it to 405px against the same content. Both measured with
`getBoundingClientRect`, not eyeballed. Re-verified with a fresh build and
screenshots at 1440px and 375px after all of the above.
