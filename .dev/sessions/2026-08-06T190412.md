Gave the marketing pages their own navbar and footer, correcting a misreading in the stage 1 port earlier today. Nothing pushed.

---

**What was wrong.** Stage 1 shipped the marketing pages wearing the documentation's navbar: Develop, Deploy, Use, Community. Raised in review with a screenshot of what the marketing navigation should be. The roadmap's "do not port the chrome" item was read as "marketing pages use the docs navbar", but what it actually said was that `docusaurus.config.ts` supplies *a* navbar so `NavBar`, `MegaMenu`, `MegaMenuLink`, `NavLink` and `useSSRWorkaround` need not be ported. Nothing in the plan said the two sites should share navigation, and sharing it made them read as one site.

**The fix.** One build still serves both, so it now serves two sets of chrome.

- `marketing/components/MarketingNavbar.tsx`: Products, Documentation, Case Studies, Services, About Us, Support, plus the "Check us out on GitHub" and "Get Started" buttons, matching the navigation the Gatsby site shipped
- `marketing/components/MarketingFooter.tsx`: the OICR logo, the six-link row, the copyright line and the Privacy / Terms / Acknowledgements row
- `src/theme/Navbar/` and `src/theme/Footer/`: swizzle wrappers that render either the marketing chrome or the untouched original
- `marketing/useIsMarketingRoute.ts`: the route test both wrappers use. It asks about the route rather than the build, so it still works after stage 3 splits the two hostnames into separate builds

Both components are written against Bulma directly rather than ported from the Gatsby class components. The megamenu was already unreachable and stays gone, and the mobile menu is a single `useState` instead of the `useSSRWorkaround` machinery Gatsby's rehydration needed.

**One real bug, caught by checking rather than assuming.** The first version put `className="marketing NavHeader"` on the same element. The partials compile to descendant selectors (`.marketing .NavHeader`), so both classes on one element match nothing and the navbar would have shipped unstyled. Found by grepping the built CSS for how `NavHeader` is actually selected and comparing that against the class attribute in the built HTML. Fixed by wrapping each in a `.marketing` div, which is now noted in both components and in the roadmap, since the next person adding chrome will hit it.

**A related regression, avoided.** Stage 1 had dropped four Bulma navbar variable overrides on the grounds that the chrome was not ported. With the navbar back they matter again, `$navbar-breakpoint` most of all: the `navmenu-up` and `navmenu-below` mixins in `_variables.scss` are written against 1160px, and Bulma's default is 1024px, so the burger and the stylesheet would have disagreed about when to collapse. Restored, along with the two `a.navbar-item` hover rules from the old `main.scss`.

**Verified per route in the built HTML**, not just at the aggregate: all nine marketing pages carry `NavHeader` and the marketing footer and no `navbar--fixed-top`; `/develop/`, `/deploy/`, `/use/` and `/community/support/` are the exact inverse. `npm run typecheck` clean, build clean apart from the known false-positive anchor warning.

**Left for the stage 2 styling review**, since neither can be checked from a build log: the navbar and footer at narrow widths, where the burger is new code rather than a port; and the fact that the Documentation and Support nav links are absolute `docs.overture.bio` URLs, which is correct per the hostnames decision but means a branch deploy cannot be clicked through end to end.
